# 训练数据流

本文档描述当前哪些数据源影响训练，哪些只是录制供将来使用。

配套说明模型拆分、头模式以及哪个训练器更新哪个网络的文档见：

- `STS2AI/docs/网络与训练概览.md`

## 主要数据源

- 在线非战斗 PPO rollout
  - 从实时自对弈 episode 收集到 `ppo_buffer`。
  - 仍然是主要的非战斗训练信号。
  - 合并时深层运行会被上加权，所以后期楼层的 episode 更重要。

- 在线战斗 PPO rollout
  - 仅从战斗 NN 自身选择动作的战斗步骤中收集。
  - 仍然是主要的在线战斗学习信号。
  - MCTS 选择的战斗动作不存入此 buffer。

- 在线战斗搜索样本
  - 仅在 MCTS 启用时产生。
  - 质量更高但成本更高的战斗监督。
  - 最好理解为战斗质量增强器，不是所有 rollout 的替代品。

- 离线非战斗排序数据
  - 配置别名：`offline_noncombat_ranking_*`
  - 用于塑形卡牌奖励 / 商店 / 篝火风格的排序行为。
  - 这是在线 PPO 之上的辅助 loss，不是主导信号。

- 离线非战斗排序头模式
  - 配置：`offline_noncombat_ranking_head_mode`
  - 仅控制离线非战斗排序监督使用的评分器。
  - `mlp` 保留传统选项评分器。
  - `light_attention` 在屏幕上下文加候选选项之上添加残差注意力块。
  - 这是尝试在卡牌奖励 / 商店风格决策上使用 Transformer 风格结构最安全的第一个地方，
    因为它不会替换整个非战斗 PPO 主干。

- 离线战斗教师数据
  - 配置别名：`offline_combat_teacher_*`
  - 回合求解器或教师标注的战斗状态，用于重排序 / 纠正。
  - 在 `train_hybrid.py` 内部同样是辅助的，除非提高其更新次数和 loss 权重。

- 主战斗 rollout 路径模式
  - 配置：`combat_main_path_mode`
  - 控制 rollout 中使用的真实战斗 `policy/value` 路径的结构。
  - `mlp` 保留传统主路径。
  - `light_attention` 在主路径上添加残差状态/动作注意力分支。
  - 应通过 `train_hybrid.py` A/B 来评测，不要仅通过教师 checkpoint 微调来评测。

- 保存的离线 episode
  - 配置别名：`saved_offline_episodes_*`
  - 高质量 episode 作为原始材料写入磁盘，供将来数据集构建使用。
  - 它们不会自动反馈到同一次训练运行中。

## 当前实际指南

- 如果你在做端到端混合模型训练，实时 rollout 数据仍然占主导。
- 如果想让离线战斗教师数据更有影响力，先增加：
  - `offline_combat_teacher_updates_per_iter`
  - 然后才考虑增加 `offline_combat_teacher_loss_weight`
- 如果想让离线非战斗排序数据更有影响力，先增加：
  - `offline_noncombat_ranking_updates_per_iter`
  - 然后才考虑增加 `offline_noncombat_ranking_loss_weight`
- 如果想测试新的非战斗排序评分器结构，改变：
  - `offline_noncombat_ranking_head_mode`
  - 同时保持非战斗主干的其余部分不变

## 为什么这很重要

固定的 loss 权重不会随着数据集大小变化自动保持公平。

例子：

- 战斗教师数据集从 `200` 增长到 `2000` 条样本，不会自动变得更有影响力。
- 在固定 batch size 和每迭代一次更新的情况下，更大的数据集被采样得更稀疏。
- 这意味着"更多离线数据"和"更强的训练信号"不是一回事。

## 推荐当前用法

- 测试新的教师数据集或评分器架构时，先单独训练战斗教师 checkpoint。
- 如果想测试新的主战斗路径结构，在 `train_hybrid.py` 中做，
  这样 rollout 脑是在在线 PPO/战斗训练下更新的，
  而不仅仅在选定的教师状态上。
- 之后，以更高的更新次数将更强的教师重新引入 `train_hybrid.py`。
- 保持路线先验和非战斗排序实验与战斗教师实验分开，这样回归更容易解读。

## 我们改了什么

| 层级 | 文件 | 改了什么 |
|------|------|---------|
| **协议定义层** | `FullRunApiStateDtos.cs` | 扩展 DTO（加了 stars/orbs/piles/counter），这是两边共享的 **合同** |
| **Sim 填充层** | `FullRunApiStateBuilder.cs` | Sim 端按新合同填充字段（stars/orbs/pile内容/IsVisible过滤） |
| **Spectator 转换层** | `SpectatorApiStateBuilder.cs` ★新建★ | 把现有 dict 输出转成同一套 DTO |
| **Spectator HTTP层** | `ModFullRunEnv.cs` | v2 API 改为输出 DTO 序列化的 JSON |

## 没改什么

- **Python 训练代码**：不需要改，收到的 JSON 结构一致
- **游戏状态读取逻辑**：`McpMod.StateBuilder.cs` 的 `BuildGameState()` 完全没动，它本来就是正确的
- **Sim 的游戏逻辑**：reset/step/action 执行全没动
- **Spectator 的 v1 API**：调试/工具用的旧接口保持不动
- **IPC 传输层**：pipe client / HTTP client 都不需要改

**核心思路就一句话：两边序列化同一个 C# 类（`FullRunApiState`），JSON 自然一致。**
