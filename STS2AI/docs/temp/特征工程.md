# 1. 设计目标与旧方案问题总结

本项目需要的不是一个“更大的 state vector”，而是一套**更合理的战斗世界表示**。这点在 STS2 上尤其重要：官方目前明确把游戏定位为 Early Access，Steam 页面写明当前是五个角色，FAQ 也明确后续会继续加入和调整角色、cards、relics、potions、enemies、events，以及 enchantments、afflictions、Ancients、alternate acts 等内容。也就是说，架构必须从第一天起就按“内容持续扩展、机制持续演化”的前提设计，而不是围绕当前卡池和 boss 名单做一次性特化。 ([Steam 商店][1])

旧方案的问题，不在于“模型不够大”，而在于**抽象层级错误**。它把本应分层处理的信息——实体语义、运行时实例、机制节点、规则改写、序列历史、动作候选——混进一个 patch/gate/aux/delta 式的表示管线里，导致三个后果。

第一，**状态表示失真**。build、当前局面、boss 机制、牌序历史、动作语义被挤进同一表示通道，模型必须先自己猜“哪些信息是慢变量、哪些是快变量、哪些会改写规则、哪些只改一点数值”。这会浪费大量容量。

第二，**动作评估失真**。旧结构里动作通常只是 state 的附属对象；但在 STS2 中，动作的价值高度依赖当前规则世界。打出同一张牌，在 damage cap、target restriction、phase threshold、window open 与否不同的情况下，价值会完全不同。

第三，**搜索接口失真**。如果 leaf evaluation 只是普通 value head 的直接外推，搜索在复杂 boss 机制前会经常停在“看起来局面不差，实际上下一拍暴毙”或“当前收益不高，但这是唯一正确铺垫”的中间局面，难以稳定做出高质量叶子判断。

因此，新架构的目标不是修旧网络，而是建立一套**长期可扩展的、机制可组合的战斗表示与决策框架**。

# 2. STS2 战斗 AI 的本质难点

STS2 战斗的难点，不是感知，而是**规则组合与时序组合**。

第一层难点是**实体异质性**。手牌、遗物、药水、敌人、召唤物、牌堆、buff、本回合事件，它们语义完全不同，但又同时参与一个动作决策。

第二层难点是**动作价值不静态**。一张牌的价值不是卡面固定值，而是当前 build、当前手牌组成、当前格挡、当前 buff/debuff、当前机制阶段、当前已出牌序列共同决定的。换句话说，动作不是“固定技能”，而是“上下文相关假设”。

第三层难点是**机制不是普通数值状态**。phase transition、window、summon cycle、damage cap、target restriction 等都不是“再多一个 scalar”就能表达清楚的东西。它们会改变动作排序、目标优先级、资源保留逻辑，甚至改变“这回合该不该 all-in”。

第四层难点是**回合内顺序敏感**。很多价值不来自单卡，而来自顺序：先上 buff 再打 finisher，先叠 block 再打按 block 转伤害的牌，先抽牌再延长连段，先 exhaust 再触发相关收益。prefix 不是状态的小修正，而是决策核心。

第五层难点是**搜索终局不充分**。大多数搜索不会把整场战斗搜完，而会停在一个中间局面。这个中间局面是否好，不只取决于敌我血量，还取决于低血非线性风险、资源保留、牌堆结构、转阶段风险、窗口是否将开、当前规则对动作的压制程度。

所以，STS2 战斗 AI 的本质不是“在状态上分类动作”，而是：

**在一个持续变化的规则世界里，对上下文相关动作假设做比较，并对中间局面做机制感知的价值判断。**

# 3. 新架构的核心设计原则

## 原则一：世界表示优先于参数规模

新架构首先要回答“这个世界由哪些对象和规则组成”，再讨论网络宽度和层数。更大的 state vector 不能替代更好的世界分解。

## 原则二：慢变量与快变量分离

build 是慢变量；当前战场是快变量；回合内牌序是更快的局部历史。它们不能被同样对待。

## 原则三：状态与规则分离

“现在处于什么阶段”和“当前规则被如何改写”是两回事。把二者都塞进 buff list，会让网络把状态机位置和结算规则混为一谈。

## 原则四：动作先条件化，再比较

网络不应只编码“动作是什么”，而应先形成“这个动作在当前 state + mechanism + modifier + history 下意味着什么”的 action hypothesis，再做排序和选择。

## 原则五：搜索与学习共设计

policy、value、search、leaf evaluator 不是彼此外挂。主干表示必须天然兼容这四者：policy 需要动作排序，value 需要全局局面判断，search 需要局部精确展开，leaf evaluator 需要机制感知的叶子评分。

## 原则六：扩展通过 schema，不通过 boss 专属分支

面对新 boss、新卡、新机制，优先新增通用机制原语、modifier 原语和 schema 配置，而不是写一批新的专属网络支路或手工 if/else。

# 4. 顶层抽象：Entity / Runtime / Mechanism / Modifier / History / Action Hypothesis

这六层是整个新架构的核心。

## 4.1 Entity Semantics

Entity Semantics 表示“这个实体本体是什么”。

它适用于 card、relic、potion、enemy，也可以扩展到 summon、特定场景对象。它包含：

* 静态类别语义
* 规则模板语义
* 关键词、标签、symbol 语义
* 不随战斗即时变化的结构信息

它回答的是：“这张牌/这个敌人原本的规则身份是什么”。

它**不回答**：

* 这张牌当前 cost 多少
* 这张牌当前伤害多少
* 这个敌人现在还有几层 shield
* 当前是不是窗口期

这些都属于后面的层。

## 4.2 Runtime Instances

Runtime Instance 表示“这个实体在当前战斗里的实例状态是什么”。

同一张 card 的静态语义不变，但它的实例状态会变：当前 cost、是否升级、是否 retain、是否被减费、当前伤害估计、当前格挡估计、是否被某 relic 或 modifier 改写。敌人也一样：静态 enemy semantic 不变，但当前 HP、block、intent、buff 层数、charges、stacks 都会变。

所以：

* **Entity Semantic** 是类定义
* **Runtime Instance** 是当前实例

这也是为什么不能把“state”和“entity”混在一起。实体本体不等于当前实例。

## 4.3 Mechanism States

Mechanism State 表示“当前处于哪个机制节点 / 状态机阶段”。

它描述的是**流程位置**，不是规则本身。典型字段包括：

* phase
* threshold pending / remaining
* window state / turns left
* summon cycle step
* shield layers 作为进度
* enraged / exposed / dormant 等阶段标签

它回答的是：

* 现在剧情进展到哪一步
* 离下一个机制节点还有多远
* 接下来可能发生什么

Mechanism State 主要影响：

* 节奏判断
* 资源保留
* 跨阶段策略
* 目标优先级
* 何时等待、何时爆发

## 4.4 Rule Modifiers / Active Rules

Rule Modifier 表示“当前有哪些规则条款在生效”。

它不是流程位置，而是**规则改写**。典型例子：

* damage cap / per-hit cap / per-turn cap
* target restriction / untargetable
* effect scaling by block
* effect scaling by hand composition
* on-play trigger modification
* draw modifier / exhaust modifier
* on-kill reward/penalty
* phase transition effect
* reflect / retaliation / beat-of-death 类规则

它回答的是：

* 当前动作怎么算
* 目标是否可选
* 哪类动作被压制或被放大
* 某效果会不会触发额外规则

Mechanism 和 Modifier 不能简单都当成 buff，因为它们在 AI 表达中承担不同职责：

* **Mechanism State**：告诉网络“当前战斗进程到了哪里”
* **Rule Modifier**：告诉网络“当前规则说明书被改成什么样”

一个 raw buff 在游戏实现中可能同时产生两种作用：
它可能一方面标记“进入 shielded phase”（Mechanism），另一方面启用“每次只受 1 点伤害”（Modifier）。对 AI 来说，这两部分必须拆开。

## 4.5 History / Prefix

History 表示“这回合到当前为止已经发生了什么”。

它不是普通状态摘要，而是有序历史，包括：

* 已执行动作序列
* source/target 顺序
* 每步资源变化
* 已触发条件
* 当前 turn 内已建立的连段、减费、增伤、exhaust、draw chain 等

它回答的是：

* 这个回合前面已经铺了什么
* 哪些条件已经满足
* 哪些动作因为前缀而升值或贬值

History 不应只变成一个 prefix summary 塞进 state，因为不同候选动作关心 history 的部分不同。

## 4.6 Action Hypothesis / Contextualized Action

这是整个架构最关键的抽象。

**Action token** 只表示动作描述：打哪张牌、打哪个目标、是否 end turn。
**Action hypothesis** 则表示：在当前 runtime + mechanism + modifier + history 下，这个动作真正意味着什么。

它包含：

* 当前即时效果的上下文求值
* 当前合法性
* 目标作用方式
* 对规则的触发与响应
* 对后续动作空间的影响摘要
* 对资源、牌堆、阶段、窗口的影响摘要

所以新架构不应比较“原始动作”，而应比较**上下文条件化后的动作假设**。

# 5. 新架构总览（模块图的文字说明）

新架构由三个大层次组成。

## 5.1 世界表示层

负责把底层战斗世界变成结构化表征：

* Entity Semantic Compiler
* Runtime Instance Encoder
* Mechanism State Encoder
* Active Modifier Encoder
* History / Prefix Encoder
* Build Memory Encoder

这一层的目标，是构建一个**可读的当前规则世界**。

## 5.2 动作上下文化与决策层

负责把候选动作转成 action hypotheses，并进行比较：

* Raw Action Candidate Builder
* Action Contextualizer / Hypothesis Builder
* Decision Core

这一层的目标，是在当前规则世界下，对“现在可做什么”形成高质量比较。

## 5.3 评估与搜索接口层

负责把主干表示接到搜索与训练：

* Policy head
* Value heads
* Boss-aware Leaf Evaluator
* Search Interface
* Training Interface

这一层的目标，是让网络既能直接决策，也能为搜索提供先验和叶子评分。

简化地说，信息流是：

**规则系统/模拟器** 提供底层真实状态与合法动作
→ **世界表示层** 构建当前规则世界
→ **动作上下文化层** 把 raw action 变成 contextualized action hypothesis
→ **决策层** 排序动作
→ **评估层** 输出多种 value 与 leaf evaluation
→ **搜索层** 在此基础上展开局部精确推演

# 6. 每个模块的职责、输入、输出、为什么这样设计

## 6.1 Entity Semantic Compiler

**职责**：把 card/relic/potion/enemy 的静态规则身份编译成统一语义空间。
**输入**：ID、静态属性、结构化规则模板、标签/关键词/symbol。
**输出**：entity semantic representations。
**为什么这样设计**：这样新实体接入时，只需补齐静态语义，不必改主干结构。

## 6.2 Runtime Instance Encoder

**职责**：表示实体在当前战斗中的实例状态。
**输入**：当前 cost、当前 HP、block、当前 stacks、当前 enhancement、当前牌面动态值等。
**输出**：runtime instance representations。
**为什么这样设计**：同一实体静态语义不变，但当前实例价值会剧烈变化；二者必须区分，否则网络无法处理动态数值卡。

## 6.3 Build Memory Encoder

**职责**：把 deck、relic、potion、角色长期能力压成可查询的 slow memory。
**输入**：本局 build 的 entity semantics 与关键 runtime summary。
**输出**：build memory。
**为什么这样设计**：build 决定“这局怎么赢”，它是长期策略上下文，不该与当前 battle scalars 一起被频繁重写。

## 6.4 Board Encoder

**职责**：表示当前快变量战场。
**输入**：我方当前状态、手牌实例、敌人当前状态、牌堆摘要。
**输出**：board representation。
**为什么这样设计**：board 只回答“现在局面是什么”，不承担机制图、规则条款、长期 build 和记忆职责。

## 6.5 Mechanism State Encoder

**职责**：表示流程节点与状态机位置。
**输入**：当前阶段、threshold、window、summon cycle、shield progress 等。
**输出**：mechanism state representations。
**为什么这样设计**：复杂 boss 真正难点在于状态机位置，而不是单个 buff 层数。

## 6.6 Active Modifier Encoder

**职责**：表示当前生效的规则改写集。
**输入**：damage cap、target restriction、effect scaling、draw/exhaust modifier、on-play/on-hit/on-kill/on-end-turn trigger 等。
**输出**：modifier representations。
**为什么这样设计**：复杂规则最怕被埋在普通 state 里。Modifier 必须作为“当前规则条款集”显式存在，才能稳定改变动作求值。

## 6.7 History / Prefix Encoder

**职责**：表示当前回合已经发生的有序前缀。
**输入**：已执行动作、顺序、资源变化、关键触发事件。
**输出**：history/prefix memory。
**为什么这样设计**：牌序不是局部修正项，而是动作价值的重要决定因素。

## 6.8 Raw Action Candidate Builder

**职责**：列出当前合法原始动作。
**输入**：模拟器合法动作列表。
**输出**：raw action candidates。
**为什么这样设计**：动作合法性应由规则系统保证，网络不负责发明非法动作。

## 6.9 Action Contextualizer / Hypothesis Builder

**职责**：把 raw action 变成 action hypothesis。
**输入**：raw action + board + mechanism + modifiers + history + runtime card state + build memory。
**输出**：contextualized action hypotheses。
**为什么这样设计**：真正决策对象不是动作描述，而是“动作在当前世界里实际意味着什么”。

## 6.10 Decision Core

**职责**：对多个 action hypotheses 做比较、排序、选择。
**输入**：action hypotheses + build memory + board + mechanism + modifiers + history。
**输出**：policy prior / action ranking。
**为什么这样设计**：决策不应由单个 state vector 对动作做打分，而应由动作读世界后再比较。

## 6.11 Value Heads

**职责**：学习通用 amortized 价值判断。
**输入**：全局战斗表征。
**输出**：如胜率、期望 HP 损失、短期生存概率、节奏优势等。
**为什么这样设计**：单一 value 难以承载全部风险维度。

## 6.12 Boss-aware Leaf Evaluator

**职责**：在搜索叶子处进行机制感知的局面评估。
**输入**：全局战斗表征 + mechanism/modifier/resource summaries。
**输出**：leaf utility。
**为什么这样设计**：普通 value head 不是叶子评估器的替代品，尤其在有限深度搜索下。

# 7. 信息流与注意力/读取关系

新架构的注意力设计，核心不是“所有 token 全拼一起再 self-attention”，而是**谁需要读谁**。

## 7.1 Build 是 slow memory，不是普通状态特征

动作在决策时必须读取 build memory，因为 build 决定长期优先级：这套牌偏铺垫、偏爆发、偏循环、偏 attrition，决定相同动作在不同 run 中的基础价值是否应被抬高或压低。

因此，build 应作为被查询的 memory，而不是随 board 一起每步重编码的普通 token。

## 7.2 Prefix 是 history memory，不是 state 的附属项

动作必须直接读取 prefix memory，因为不同动作关心不同前缀片段。Finisher 关心“前面 buff 是否到位”，draw extender 关心“当前链是否能延长”，end turn 关心“该铺的是否已经铺完”。

所以，prefix 不应只是压成一个向量加到 state，而应作为独立 memory 被动作直接查询。

## 7.3 Mechanism 与 Modifier 都应被动作直接读取

动作排序受机制和规则共同影响：

* Mechanism 决定“现在是否窗口期、是否临近转阶段、是否该保资源”
* Modifier 决定“这张牌现在按什么规则结算、是否被压制、目标是否合法”

因此，action hypothesis 的形成过程必须直接读取 mechanism 和 modifier，而不只是让 state 代读。

## 7.4 不推荐统一大熔炉式 self-attention

把 build、board、mechanism、modifier、history、actions 一开始全丢进一个大 self-attention，会混淆时间尺度与作用对象。更合理的设计，是先构建世界表示，再让 action hypotheses 去查询它们。

## 7.5 建议的读取顺序

从架构意义上，最自然的顺序是：

1. 动作先读取 runtime/board，知道当前局面基础条件
2. 再读取 modifiers，理解当前结算规则
3. 再读取 mechanisms，理解当前机制节奏与阶段风险
4. 再读取 history，理解当前回合前缀
5. 最后由 build memory 对整个动作价值做长期调制

这不是唯一顺序，但它符合“当前可执行性 → 当前规则 → 当前阶段 → 当前前缀 → 长期策略”的认知层次。

# 8. 复杂 boss 机制的表达方式

这里是新架构的核心能力验证。

## 8.1 Phase transition

表达方式不是只给 phase_id，而是同时区分：

* Mechanism State：当前 phase、threshold pending、threshold remaining、next phase identity
* Rule Modifier：转阶段触发时会带来的规则改变，如目标限制、伤害规则变化、状态重置等

这样网络能同时知道：

* 现在在什么阶段
* 再打多少会转
* 转了之后规则会怎么变

## 8.2 Window open / close

窗口本质是机制节点，不是普通 buff。
表达方式：

* Mechanism State：window_state、window_turns_left、window_trigger_condition
* Modifier：窗口期间哪些动作被放大或解禁

## 8.3 Summon cycle

召唤是状态机过程。
表达方式：

* Mechanism State：summon_cycle_step、summon_countdown、main_body_exposed
* Modifier：本体是否可选、击杀 adds 是否触发规则变化、adds 存活是否给本体额外保护

## 8.4 Damage cap / per-hit cap

cap 本身是规则，不是机制进度。
表达方式：

* Mechanism State：cap 是否由某阶段或某护盾状态触发
* Modifier：damage cap type、cap value、scope、duration

这能让动作明确感知“大单段伤害”和“多段伤害”在当前世界中的相对价值。

## 8.5 Target restriction

目标限制属于规则条款。
表达方式：

* Modifier：untargetable scope、must kill adds first、only target exposed core 等

若限制是由某机制阶段触发，则阶段本身属于 Mechanism，限制条款属于 Modifier。

## 8.6 多阶段 boss 的跨阶段策略

跨阶段策略需要同时利用：

* Mechanism：转阶段距离、下一阶段标签、窗口是否即将打开
* Modifier：下一阶段将生效的规则
* History：本回合是否已经交了关键资源
* Build：本套牌是更适合跨阶段保资源，还是当前窗口爆发

这就是为什么 build、mechanism、modifier、history 必须同时存在。

# 9. 动态卡牌数值、抽牌、消耗、联动的表达方式

## 9.1 Runtime Card State 是必需层

动态卡牌不能只靠静态 semantic 表示。
需要单独表达当前实例状态，如：

* 当前 cost
* 当前伤害/格挡估计
* 当前 scaling 来源
* 当前 conditional 是否激活
* 当前受哪些 modifier 影响

这不是实现细节，而是抽象边界：
**卡的静态身份** 不等于 **卡此刻能做什么**。

## 9.2 scale-by-block / scale-by-hand-composition

这类效果不应只是卡牌标签。
表达方式：

* Entity Semantic：这张牌具备该规则模板
* Runtime Instance：当前 block、当前 hand subtype composition
* Modifier：若该关系又被额外规则放大/抑制
* Action Hypothesis：当前动作在此规则下的实际估值

## 9.3 Draw 的表达

抽牌不是“立即收益 +2”那么简单，而是改变后续动作空间。
因此，它必须同时进入：

* Runtime State：当前 draw/discard/exhaust 结构
* History：当前回合已发生的 draw 链
* Action Hypothesis：该动作对后续动作空间的影响摘要

## 9.4 Exhaust 的表达

exhaust 不是简单消失，而是改变本战斗的牌堆结构与联动强度。
因此，它必须进入：

* Runtime State：当前 pile 结构
* Modifier：是否存在 exhaust-related trigger
* Action Hypothesis：该动作对后续牌堆与触发规则的影响摘要

## 9.5 联动不应靠模型自己纯文本悟

draw、exhaust、block-scaling、hand-composition-scaling 等机制，规则系统本来就知道。
因此：

* **模拟器/规则系统** 负责精确求值与上下文求值输入
* **网络** 负责在 build、机制、牌序上下文中决定何时、对谁、以什么顺序使用这些动作

---

# 10. 搜索接口与 Leaf Evaluator 设计

## 10.1 为什么单纯 value head 不够

普通 value head 是学习型、摊销型的局面判断器，适合全局快速估值。
但 leaf evaluator 面对的是有限深度搜索后的中间局面，它需要更稳定地处理：

* 非线性低血风险
* 资源保留价值
* 转阶段风险
* 当前 modifier 导致的动作无效率
* 窗口是否即将开启或关闭

普通 value head 容易把这些不同风险压成一个平均值，从而在关键 boss 状态下失真。

## 10.2 Leaf Evaluator 的职责

Leaf evaluator 不是另一个普通 head，而是**搜索时间的机制感知局面效用层**。
它应综合：

* learned global value
* non-linear HP utility
* short-horizon survival risk
* resource retention value
* transition risk
* modifier inefficiency penalty
* window utilization potential

## 10.3 为什么 HP utility 要非线性

在高血时掉 10 血与在低血时掉 10 血，不应等价。
搜索如果不显式非线性处理生存边际价值，就会在低血 boss 战中高估“当前回合输出赚了”的路径。

## 10.4 为什么需要 boss-aware penalty hooks

这里的“boss-aware”不意味着为每个 boss 写专属 heuristic，而是对**通用 modifier / mechanism 原语**定义可解释 penalty 或 reward：

* damage cap 下的高额无效率动作惩罚
* target restriction 下的错误目标惩罚
* threshold 即将触发时的 transition risk
* 窗口期未利用或窗口外盲目 all-in 的节奏损失
* 资源在跨阶段前被错误耗尽的惩罚

这应是**原语级**，不是 boss 名字级。

## 10.5 搜索接口

搜索层应消化三类输入：

* policy prior：哪些 action hypotheses 更可能好
* state/action features：用于局部展开与排序
* leaf evaluator：在截断深度处给出更可靠的局面效用

这使搜索不再只是“policy head + rollout”，而是完整的“先验 + 精确展开 + 专门叶子评估”。

# 11. 训练接口（PPO / imitation / ranking / search distillation）

## 11.1 训练目标必须分层

训练不应只剩一个 PPO loss。应当至少兼容四类监督：

* imitation：学习基本打法与人类/搜索老师行为
* ranking / preference：学习动作相对排序
* value learning：学习全局摊销局面价值
* leaf evaluator learning：学习局部搜索终点的高质量局面判定

## 11.2 PPO 只负责 on-policy 改进，不应独吞全部学习

PPO 适合在已有较强表示与行为先验基础上做在线微调。
如果把“理解机制、理解牌序、理解复杂 boss”全部押注到 PPO 上，它会被自然样本分布拖向杂兵优化。

## 11.3 如何避免训练时杂兵分布主导

训练样本不应按自然房间频率等权处理。
需要至少按以下维度做分层：

* room type：normal / elite / boss
* mechanism family：phase、window、summon、damage rule 等
* risk level：稳定局面、near-lethal、transition pending、窗口期
* build family：爆发、成长、循环、控制等

PPO 的 rollout 来源也应分层，而不只是自然 run 采样。

## 11.4 搜索蒸馏的角色

搜索不应只在推理时用，也应在训练中回灌：

* 关键机制状态 top-k action ranking
* leaf evaluator target
* transition-sensitive preference
* 稀有 boss 状态的更强局部老师

这样可以显著缓解复杂机制样本稀疏。

## 11.5 复杂机制状态必须高权重

复杂机制状态之所以难，不是模型不知道它们存在，而是它们在自然分布中稀、在错误时损失大。
因此训练体系必须显式提升这类状态的覆盖率和损失权重。

# 12. 可扩展性设计：未来新机制如何接入

由于官方明确说明 STS2 在 Early Access 期间仍会继续加入和重平衡大量内容与新机制，本架构必须把“未来机制接入”视为正常流程，而不是异常变更。 ([Mega Crit Games][2])

## 12.1 什么由模拟器 / 规则系统负责

模拟器 / 规则系统应负责：

* 战斗权威状态
* 合法动作生成
* 原始运行时数值
* 机制状态与 modifier 的编译
* runtime card state 的精确求值
* raw action 的即时上下文化信息

也就是说，**规则求值与合法性**应由系统负责，不应交给神经网络去从零猜。

## 12.2 什么由网络负责学习

网络应负责：

* build 与当前局面的策略整合
* 历史敏感的动作排序
* 不同机制组合下的泛化
* 对局面长期价值与中间风险的判断
* 为搜索提供 priors 与 learned value / evaluator features

## 12.3 新机制接入的理想路径

理想情况下，新机制接入只需要：

1. 在通用 mechanism primitive 库中复用或新增一个 primitive
2. 在通用 modifier primitive 库中复用或新增一个 primitive
3. 在规则系统中新增对应 schema / 配置
4. 由编译器产出统一格式的 mechanism/modifier/runtime/action fields

主干网络不变，训练继续。

## 12.4 为什么不接受纯 boss 专属逻辑

纯 boss 专属逻辑的问题不是“写不出来”，而是：

* 难维护
* 不能泛化
* 不利于新机制复用
* 会把训练和搜索绑死在特例实现上

架构应追求的是**通用机制原语**，而不是 boss 名字级专属 if/else。

# 13. 与旧方案相比的本质升级

旧方案的核心假设是：

* 先有一个状态表示
* 再有一个动作表示
* 最后让二者发生一次交互并打分

新方案的核心假设是：

* 先构建一个当前规则世界
* 再把每个动作条件化成 action hypothesis
* 最后比较这些 hypotheses，并由专门 evaluator 评估叶子局面

这带来四个本质升级。

**第一，表示升级。**
从“混合向量”升级为“世界模型式分层表示”。

**第二，动作升级。**
从“动作描述”升级为“上下文相关动作假设”。

**第三，机制升级。**
从“把 boss 机制埋在 buff/state 里”升级为“机制状态 + 规则条款双层表示”。

**第四，搜索升级。**
从“普通 value 截断”升级为“机制感知 leaf evaluator”。

# 14. 风险点、未决问题、需要后续验证的地方

## 14.1 Mechanism / Modifier primitive 的边界需要打磨

这是最重要的 schema 设计工作。边界太粗会丢信息，边界太细会导致配置爆炸。

## 14.2 Runtime card state 的求值范围要谨慎

如果上下文化过度依赖深层模拟，动作求值会变得昂贵；如果过于简化，又会丢掉 draw/exhaust/联动价值。

## 14.3 Leaf evaluator 的“learned vs structured”比例需要验证

纯 learned 容易对稀有机制不稳；纯手工又难扩展。需要在通用原语级结构化项与学习型项之间找到平衡。

## 14.4 History 长度和粒度需要实验

不是历史越长越好。关键是保留真正会重排动作排序的前缀信息。

## 14.5 Build memory 的更新频率需要明确

理论上它是 slow memory，但某些战斗内成长也会改变“当前 build 的实现状态”。需要区分“build identity”与“战斗内 build realization”。

## 14.6 搜索与训练闭环需要验证

理想上，搜索为训练提供老师，训练再反哺搜索 priors 与 evaluator；但不同阶段的比重、数据混合与稳定性需要实验。

# 15. 最终推荐架构总结

最终推荐的版本，不是“大号 state vector + 动作打分器”，而是：

## 顶层结构

**Entity Semantics**
→ **Runtime Instances**
→ **Mechanism States**
→ **Rule Modifiers / Active Rules**
→ **History / Prefix**
→ **Action Hypotheses**
→ **Decision Core**
→ **Policy / Value / Leaf Evaluator**

## 核心判断

* build 应该是 **slow memory**
* prefix 应该是 **independent history memory**
* boss 复杂机制应该被拆成 **Mechanism State + Rule Modifier**
* 动作比较对象应该是 **Action Hypothesis**，不是 raw action token
* 搜索叶子评估应该是 **独立层**，不是普通 value head 的附属品

## 系统边界

* **模拟器 / 规则系统**：负责真实规则、合法动作、状态编译、modifier 编译、runtime 求值
* **神经网络**：负责跨 build、跨机制、跨前缀的策略比较与价值判断
* **搜索**：负责局部精确推演与叶子机制评估
* **训练系统**：负责把 imitation、ranking、value、search distillation、PPO 组织成闭环

## 最终目标

让架构能够随着 STS2 的内容扩展持续演化，而不是每新增一个 boss、一个规则、一个机制，就去重写主干逻辑。

这份设计的核心不是“怎么更快实现”，而是先把世界表示、机制边界、动作语义和搜索接口设计对。只要这四件事设计对，后续实现才有长期价值。
