# 网络与训练概览

本文档是"当前实际在训练什么"的说明，与 `训练数据流.md` 配套。

聚焦三件事：

1. 当前混合栈里有哪些网络。
2. 哪些部分是 MLP、light attention 还是 transformer 风格。
3. 哪个训练循环更新系统的哪个部分。

目标是让后续实验更容易推理。

## 高层拆分

当前栈有两个主脑：

- `FullRunPolicyNetworkV2`
  - 文件：`STS2AI/Python/core/rl_policy_v2.py`
  - 角色：非战斗 / 全局 PPO 脑
  - 负责地图、卡牌奖励、商店、篝火、事件以及共享主干/价值逻辑

- `CombatPolicyValueNetwork`
  - 文件：`STS2AI/Python/core/combat_nn.py`
  - 角色：战斗策略/价值脑
  - 负责战斗中的动作评分和战斗价值估计

还有两个训练辅助器：

- `PPOTrainerV2`
  - 文件：`STS2AI/Python/core/rl_policy_v2.py`
  - 更新全局 PPO 脑

- `CombatPPOTrainer`
  - 文件：`STS2AI/Python/train_hybrid.py`
  - 用在线战斗 PPO 数据更新战斗策略/价值脑

以及一条独立的离线微调路线：

- `train_combat_teacher.py`
  - 文件：`STS2AI/Python/search/train_combat_teacher.py`
  - 最好理解为战斗教师 / 重排序训练器
  - 不适合直接替代主 rollout 战斗脑

## 当前默认尺寸

以下是最近铁甲从零训练和 A/B 配置使用的维度。

- 共享 embedding 大小：`embed_dim = 48`
- 战斗隐藏层大小：`combat_hidden_dim = 192`
- 牌组表征大小：`deck_repr_dim = 64`
- 检索 / 符号投影大小：`retrieval_proj_dim = 16`
- PPO 主干隐藏大小：`trunk_hidden = 256`
- PPO 主干输出大小：`trunk_output = 128`
- PPO 屏幕头大小：`screen_head_dim = 128`
- 注意力头数：`num_attn_heads = 4`

重要实际说明：

- 这不是巨型 LLM 风格的栈。
- 模型仍然是一个结构化 RL 模型，带有小型注意力块。
- 目前大多数实验一次只改一个头或一条路径，而非整个系统。

### 近似参数量

对于最近的 `embed_dim=48 / combat_hidden_dim=192 / deck_repr_dim=64` 家族：

- 全局 PPO 脑：约 `1.36M` 参数
- 战斗脑：约 `1.34M` 参数
- 合并混合栈：约 `2.70M` 参数

同一家族的参考数据：

- `boss_readiness_head`：约 `11.2K`
- PPO `matchup_score_head`：约 `41.2K`
- 离线非战斗排序 transformer 块：约 `265K`
- 战斗 `policy_scorer`：约 `36.9K`
- 战斗 `value_head`：约 `18.6K`
- 战斗 `action_score_head`（教师评分器）：约 `74.1K`
- 战斗主路径注意力块：约 `148K` 注意力 + `74K` FFN

这就是项目仍能快速迭代的原因：

- 模型结构紧凑
- 目前的"transformer"实验都是局部头/路径升级
- 我们没有在训练巨型解码器模型

## 全局 PPO 脑

类：

- `FullRunPolicyNetworkV2`

主要结构：

1. 实体 embedding
2. 牌组 / 遗物 / 药水 / 手牌 / 敌人的集合编码器
3. 共享主干 MLP
4. 屏幕特定头
5. 价值头和辅助头

关键模块：

- `entity_emb`
  - 共享实体 embedding

- `deck_encoder`、`relic_encoder`、`potion_encoder`
  - 构建状态的集合编码器

- `hand_encoder`、`enemy_encoder`
  - 同时喂给全局主干的战斗感知上下文

- `trunk`
  - 标量 + 池化集合表征上的共享 MLP

- `map_head`、`card_reward_head`、`shop_head`、`rest_head`、`event_head`、`combat_head`
  - 屏幕特定策略上下文构建器

- `value_heads`
  - 屏幕特定价值头

- `deck_quality_head`
  - 辅助构建质量预测器

- `boss_readiness_head`
  - Boss 条件化的构建就绪度辅助头

### Boss 就绪度头

该头基于以下信息预测 boss 感知的就绪度分数：

- 牌组/构建表征
- 标量状态上下文
- boss 身份 embedding

它是辅助头，不是直接的动作头。

当前实际限制：

- 原始 loss 经常变得非常小。
- 在 `boss_readiness_coeff = 0.05` 下，其最终影响可能几乎可以忽略。
- 这意味着它是弱偏置，不是主导教师。

## 战斗脑

类：

- `CombatPolicyValueNetwork`

主要结构：

1. 手牌编码器
2. 敌人编码器
3. 标量状态编码器
4. 共享战斗状态表征
5. 策略评分器
6. 价值头
7. 仅教师辅助头

关键模块：

- `hand_encoder`
- `enemy_encoder`
- `state_encoder`
- `policy_scorer`
  - 主 rollout 战斗动作评分器

- `value_head`
  - 主 rollout 战斗价值头

- `action_score_head`
  - 教师 / 重排序评分头

- `continuation_value_head`
  - 教师延续目标

### 主战斗路径模式

配置：

- `combat_main_path_mode`

支持的模式：

- `mlp`
  - 传统主 rollout 路径

- `light_attention`
  - 主战斗 rollout 路径上的残差注意力增强

重要说明：

- 这改变的是 rollout 中使用的真实战斗 `policy/value` 路径。
- 应该在 `train_hybrid.py` 中评测，而不仅在 `train_combat_teacher.py` 中。

### 教师评分器路径

战斗网络还有一条独立的教师/重排序路径。

该路径适用于：

- 离线教师评分
- 纠正 / 覆盖实验
- 动作重排序

它和主 rollout 战斗脑不是同一回事。

## MLP vs Light Attention vs Transformer

这些名称并不都指相同的范围。

### `mlp`

含义：

- 传统评分器/路径保持简单的 MLP 投影 + 评分

使用场景：

- 战斗主路径
- 离线非战斗排序头
- 教师评分器基线

### `light_attention`

含义：

- 在传统表征之上添加小型残差注意力块
- 保留旧表征不变，学习一个修正

使用原因：

- 比替换整条路径风险更低
- 更好的 checkpoint 兼容性
- 更容易做 A/B 归因

使用场景：

- 战斗主 rollout 路径
- 离线非战斗排序头
- 教师评分器实验

### `transformer`

当前代码中的含义：

- 用于离线非战斗排序的更重的 transformer 风格残差上下文评分器
- 比 `light_attention` 更完整的注意力/FFN 风格交互

重要说明：

- 在当前实验中，`transformer` 仅用于
  `offline_noncombat_ranking_head_mode` 路径。
- 这不意味着整个游戏脑都是 transformer。

## 当前到底什么是 Transformer

这是最常见的困惑源。

如果一个配置写了：

- `combat_main_path_mode = "mlp"`
- `offline_noncombat_ranking_head_mode = "transformer"`

那实际含义是：

- 战斗主 rollout 脑：仍然是 MLP
- 离线非战斗排序评分器：transformer 风格

这**不**意味着"战斗和非战斗现在都是 transformer 了"。

如果战斗在使用注意力，那是由以下配置单独控制的：

- `combat_main_path_mode = "light_attention"`

## 训练循环

### 1. `train_hybrid.py`

这是主端到端训练循环。

它结合了：

- 在线非战斗 PPO rollout
- 在线战斗 PPO rollout
- 可选的离线非战斗排序更新
- 可选的离线战斗教师更新
- 可选的离线 episode 保存录制

这是评测以下内容的正确场所：

- 战斗主路径结构变更
- 端到端混合行为变更

### 2. `train_combat_teacher.py`

这是专用的离线战斗教师训练器。

最适合用于：

- 动作重排序头
- 教师 checkpoint
- 纠正模块

它**不**适合用来判断新的主 rollout 战斗路径结构。

原因：

- 它在选定的教师状态上训练
- 它不优化完整的在线 rollout 分布
- 它不能替代 PPO 风格的长期学习

## 离线数据层

有三个独立的概念。

### `saved_offline_episodes`

含义：

- 混合训练期间写入的原始 episode 录制
- 由 `EpisodeDataSaver` 输出
- 存储在每次运行的 `offline_data` 目录下

重要说明：

- 这些不会自动反馈到同一次训练运行中
- 它们是后续数据集构建的原始材料

### `offline_noncombat_ranking`

含义：

- 用于卡牌奖励 / 商店 / 篝火风格监督的清洗后排序数据集

当前示例：

- `STS2AI/Python/data/skada/derived/ironclad_matchup_bridge`

这些数据由 `train_hybrid.py` 显式加载，每个迭代都会使用。

### `offline_combat_teacher`

含义：

- 清洗后的战斗教师数据集

当前示例：

- `STS2AI/Artifacts/combat_teacher/ironclad_act1_solver_v2_dataset_320.jsonl`
- `STS2AI/Artifacts/combat_teacher/ironclad_act1_solver_v2_dataset_2000_balanced.jsonl`

这些数据同样被显式加载，启用时每个迭代都会训练。

## 为什么离线录制不等于离线训练

这是另一个常见的困惑点。

当 `saved_offline_episodes_enabled = true` 时：

- 混合训练会将有用的 episode 录制到磁盘
- 但这些文件不会自动被同一次运行重新读取

所以：

- 录制已开启
- 存储正在发生
- 但直接训练只来自显式传入的数据集：
  - `offline_noncombat_ranking_data_dir`
  - `offline_combat_teacher_data_dir`

## 当前实际结论

### 已经显示正向信号的方向

- `combat_main_path_mode = light_attention`
  - 通过 `train_hybrid.py` 训练时
  - 在之前的战斗聚焦实验中展示了正向 A/B 变化

### 尚未显示可靠增益的方向

- 更重的 transformer 风格离线非战斗排序头
  - 尤其是从成熟基线恢复时

### 当前容易误解的点

- `combat_ppo` 是训练方法名，不是网络结构名
- 当前配置中的 `transformer` 通常只指离线非战斗排序头
- `boss_readiness_loss` 在日志中可能看起来存在，但对整体梯度贡献极小

## 实际有助于调参的监控信号

以下是实验中最值得关注的信号。

### 核心结果指标

- `avg_floor`
- `boss_reach_rate`
- `act1_clear_rate`
- `boss_hp_fraction_dealt_mean`

这些告诉我们系统是否在唯一重要的意义上变强：
走得更远，把更多的游戏转化为真正的 boss 尝试。

### PPO 稳定性信号

- `ppo_entropy`
  - 越低意味着越确定，但不自动等于"更好"
  - 当楼层持平而熵持续塌缩时很危险

- `ppo_clip_fraction`
  - 当前触及裁剪边界的 PPO 样本比例
  - 高值意味着更新相对旧策略推得太猛

- `ppo_ratio_mean`
  - 平均 PPO 重要性比率
  - 用于判断策略是否偏离 rollout 策略太激进

- `ppo_ploss`、`ppo_vloss`
  - 有用，但应与楼层、熵和裁剪比例一起解读
  - 单独看策略 loss 的符号不能可靠判断好坏

### Boss 感知信号

- `boss_readiness_loss`
  - 原始辅助 MSE

- `boss_readiness_weighted`
  - 乘以 `boss_readiness_coeff` 后的实际贡献

加权版本才是诊断中重要的那个。一个看起来"存在"的原始 loss
在加权后可能在功能上完全无关紧要。

### 结构学习信号

- `offline_ranking_action_context_gate`
- `offline_ranking_state_context_gate`
- `combat_main_action_context_gate`
- `combat_main_state_context_gate`
- `combat_teacher_action_context_gate`

这些告诉我们残差注意力分支是否真正被使用。

如果一个分支已启用但门控值接近零：

- 结构存在
- 但训练还没学会依赖它

### 离线数据影响信号

- `matchup_rank_loss`
- `combat_teacher_loss`
- `training_sources.json` 中的数据集大小
- `training_flow.md` 中的更新计数

这些很关键，因为"有离线数据"和"离线数据在实质性影响这次运行"是两码事。

## 当前调参判断

基于最近的实验：

- 战斗主路径 `light_attention` 是真正有正向信号的方向。
- 离线非战斗 transformer 排序尚未显示出比简单 MLP 基线更强的端到端收益。
- `boss_readiness_coeff = 0.05` 往往使 boss 就绪度监督在原始 loss 变小后太弱而无关紧要。
- 楼层持平但熵下降是警告信号，但仅此不够；应同时检查裁剪比例和真实结果指标。
