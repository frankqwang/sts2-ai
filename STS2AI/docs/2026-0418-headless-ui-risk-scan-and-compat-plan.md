# 2026-0418 Headless UI 风险扫描与 compat 处理方案

## 1. 目标

在不修改 `src` 上游源码的前提下，找出 headless / pure-sim 下仍然可能因为 UI / 场景树假设而触发的空引用风险，并把处理方式固定为：

- 编译缺口: 继续走 runtime stub / generated stub
- 运行期 UI 依赖: 走 `STS2AI/ENV/Sim/SrcCompat` 的源码级 compat 覆盖

不建议走“伪造完整 `NGame` / `NCombatRoom` 场景树”的通用 stub。这样做会把 sim 语义绑到一套脆弱的假 UI 上，后续游戏版本更新时维护成本会更高。

脚本特点：

- 按 host 实际 `Compile Include/Remove` 解析有效源码集合，不靠硬编码目录猜测
- 默认支持 3 个范围:
  - `compiled-models`
  - `compiled-monsters`
  - `compiled-all`
- 风险只盯高危 UI 依赖:
  - `NCombatRoom.Instance.Background`
  - `NCombatRoom.Instance.GetCreatureNode(...)`
  - `NCombatRoom.Instance.(Back)CombatVfxContainer`
  - `NCombatRoom` 的表现层效果接口
  - `NGame.Instance` 的视觉/震屏/viewport 访问
  - scene/UI 可空变量后续被直接解引用

compat 候选生成脚本特点：

- 默认是 dry-run，只打印候选文件和可做的高置信 rewrite
- 只有显式 `--write-files` 才会真正写入生成目录
- 生成结果落在 `STS2AI/ENV/Sim/SrcCompat/AutoGenerated`
- host 通过静态 `Import` 自动消费生成出来的 `.props + .cs`
- 生成目录默认加入 `.gitignore`，按“可重建产物”处理，不污染手写 compat
- 当前只做高置信重写:
  - `NGame.Instance.ScreenShake/DoHitStop/...` -> `HeadlessVisualCompat`
  - `NCombatRoom.Instance.GetCreatureNode(...)` -> `HeadlessVisualCompat.TryGetCreatureNode(...)`
  - `GetSpecialNode<T>(...)` -> `HeadlessVisualCompat.TryGetSpecialNode<T>(...)`
  - `CombatVfxContainer.AddChildSafely(...)` -> helper 包装
  - `Background.GetNode<T>(...)` -> helper 包装
- 不做“盲目全量加 `?`”，避免把控制流改坏

## 5. 处理原则

### 5.1 什么适合 runtime stub

- 缺类型
- 缺接口
- 缺平台实现
- 只为让 host 编译通过的结构性依赖

### 5.2 什么不适合 runtime stub

- 依赖真实房间背景节点的攻击动画
- 依赖 `CreatureNode` / `SpecialNode` 的骨骼偏移
- 依赖 `NGame` viewport / screen shake / hit stop 的表现层逻辑

这类问题更适合在 compat 覆盖里改成：

- 有节点就播
- 没节点就跳过
- 保留真正的战斗命令语义不变

## 6. 当前结论

- 不需要改 `src`
- 不建议 fake 全量 UI scene
- 最稳的通用路线是:
  - `stub` 只管编译缺口
  - `scan` 负责找风险
  - `overlay compat` 负责消化运行期 UI 依赖
  - `generator` 负责把“机械型 compat”批量落成候选
- 对自动生成的 compat，放到 `SrcCompat/AutoGenerated`，与手写 compat 分层管理

下一步如果继续收敛，可以优先按 `compiled-monsters` 报告顺序补一批 monster compat，再做独立 smoke。
